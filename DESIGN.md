# Architecture Playground — design record

Name: Architecture Playground. What you design here is an architecture — an arrangement of machines, models, and roles — and the instrument's job is to let you try one, including the ones that will not work. "Harness" named only the software that ends up routing the tasks, and using it for the whole subject oversold the planning and undersold the playing. The word survives where it still means that software and nowhere else.

Realistic and unrealistic, both admitted. A playground that only contains good ideas cannot teach you which ideas are good. So the catalogue carries the passively cooled card that needs a shroud, the aftermarket board no vendor specifies, and the 16GB part that cannot hold the model you selected — each listed, each costed by the same arithmetic, each stating its own objection. The instrument refuses a configuration only when it genuinely cannot be built; everything else is a flag, because a constraint you can read is worth more than a choice quietly removed.

Direction: Swiss × instrument-panel blue-grey × dense × quiet
Why this subject: A hardware-and-model routing tool should feel like a legible engineering console, with firm hierarchy and measured status signals rather than decorative spectacle.
Palette: Ink `#13212a`; paper `#edf1f2`; panel `#dfe6e8`; cyan signal `#087f8c`; amber caution `#c77a15`; red limit `#b94b42`.
Type: System grotesk display / system sans body / monospace utility; compact modular scale.
Signature: Horizontal “signal lanes” that show model workers or inference phases assigned to physical hardware; the host designers use the same instrument cells to turn a GPU payload into a constrained host specification.
Reuse: The Buy and Deploy views share the same control-strip, metric-cell, and signal-lane language; the harness topology cards and the two host designers extend the system into node topologies and reference-platform constraints without changing the visual direction.
Topology: Harness arrangement is a parameter of the one Deploy surface, not a set of sibling tabs. Each of the six shapes carries an inline-SVG diagram drawn on theme tokens, its claim-state pill, and its live worker count. The counts are what make the cards informative whether or not you choose from them; the claim pills are evidence states, never a ranking.
Two presentations, one grid: mid-session the shapes are tiny at rest — a single line naming the current one — opening into a card page that keeps the topbar and tabs, titled a place ("Harness topology") because it is somewhere you already are. Reached from the start gate's topology door it is the gate's second step: full-screen with the rest of the app hidden, titled a question, and showing only the shapes. It asks nothing else: the counts are computed at the model, precision and context you are already carrying, and the note under the grid states which those were, so the assumption stays visible without being a second question. The rule the two share is that the page must never be a toll booth — it is a gate only for someone who asked for one, and every card reports real arithmetic either way.
Gate doors: three, not four. A roster is not an independent way in — whether roles apply at all is settled by the shape, and two of the six shapes have none to assign — so the roster is reached through the topology door rather than by a door of its own. A door that can land you on a panel the next choice deletes is not a starting point.
Host classes: consumer and server are two designers, not one list with a mixed dropdown. They answer different questions and have almost nothing in common at the point of choosing — one is a tower on a desk with two memory channels and sixteen graphics lanes to split, the other is a chassis with risers and an electrical plan — so each panel offers only its own platforms and only the GPU counts its boards can host. A consumer host is not a cheaper server: the x8/x8 lane split and the two memory channels are stated rather than left for the buyer to discover, because answering one RTX 3090 with an eight-channel EPYC in a 4U chassis was the most expensive wrong answer the instrument could give. They share one derivation engine and one saved-build slot: whichever panel you save from owns it, and the other panel's button says so. Memory is a costed parameter rather than a label: every capacity states the module plan that reaches it — counted in slots, not channels, because the server boards carry one DIMM per channel and the consumer boards two — and the memory's own draw enters the power estimate, so tripling a population moves the PSU target instead of leaving it identical. Where system memory falls below total VRAM the panel says so, because staging weights through the host wants room for the largest single model.

GPU catalogue: eleven cards on one list, offered identically to both designers. The panels differ in the platforms and counts they can host, which are properties of the board; they do not differ in what card you may consider, because the interesting builds are the ones that cross the line — a passively cooled L40S in a tower, an active card in a chassis planned for pressure. So cooling is a flag, never a filter: the passive board says devise a cooling solution and names what that takes, the active board in a 4U says confirm slot pitch and intake. A constraint stated is worth more than a choice removed, and the instrument has no business refusing a build that people demonstrably ship. The same reading decides the count ceilings: when a payload is refused the panel says whether the host or the card is what stopped it, because those have different answers.

Bandwidth is a first-class GPU field for the same reason capacity is. Capacity says what fits; bandwidth says how fast it decodes, and across this catalogue it spans nearly 3x while capacity repeats — three separate 48GB cards differ only here. A card's bridge is carried the same way and described at the count you actually chose, because every bridge in this catalogue joins two GPUs and the failure it invites is reading four cards as one pool. Every bandwidth here is the vendor's own published figure, which took going past the product pages to get: NVIDIA omits bandwidth from the GeForce spec tables but states it in the architecture whitepapers, and the density-optimised parts have their own datasheets separate from the flagship's. The provenance field survives that success rather than being deleted by it, because the discipline it enforces is about the next card, not this catalogue: the instrument may do arithmetic, but it may never present its own arithmetic in the same column as a quoted specification.

Three kinds of card the catalogue used to refuse. Sixteen-gigabyte boards, non-NVIDIA boards, and aftermarket rebuilds were each left out for a different reason, and each reason turned out to be a thing the instrument should say rather than a thing it should hide. The 16GB cards were excluded because the builder measured capacity against a flat 20GB constant and would have reported a working worker on a card that cannot hold one — the fix was to measure against the model actually selected, which is more honest for every card and makes the small ones self-describing. Non-NVIDIA boards were excluded because the vocabulary assumed CUDA; the fix was to make the software stack a field, so ROCm and oneAPI are named, their friction stated once, and their capability left unimpeached. Aftermarket 48GB rebuilds were excluded because no vendor specifies them; the fix was a provenance field that says exactly that, next to figures that are reported rather than published. A catalogue that omits what people actually buy is not more rigorous than one that lists it with the evidence attached — it just moves the research back onto the buyer, which is the job this instrument exists to do.

Capacity is measured against the selected model, never a constant. The flat proxy was defensible while every card in the catalogue cleared it and indefensible the moment one did not, because its floor-to-one behaviour turned "cannot run this" into "one worker". A card that does not fit reports zero and says what it would take: less precision, less context, or more memory. It stays saveable, because the model is a control the buyer may change and the tower is still a real tower — a build is invalid when it cannot be built, not when it is currently pointed at the wrong model.

Import: a model the catalogue does not carry is read from its own Hugging Face repository rather than typed in, but it never impersonates a curated entry — it lands in its own Imported group, carries an imported flag, and says which of its sizes were measured and which were estimated. The instrument may reach the network to learn a number; it may not blur where a number came from.
Import at the gate: the import control lives in the topbar, which stays visible while the start gate is up, so the panel must open there too — a visible control that does nothing when clicked is broken, whatever the layout intended. It leads the gate rather than following it, so it is seen without scrolling past a full-height question. Choosing a model is orthogonal to choosing a route, and importing first is the thing that makes the gate's own worker counts describe your model instead of a default.
Buy pages: Buy holds two pages rather than one long column. The machine page names hardware — an exact Mac configuration, a standalone system bought whole, or a host derived from a GPU payload — and the browse page compares the pre-designed builds. The four panels divide by what you are deciding: a configuration you pick, a system that arrives built, and a host derived from the payload you intend to run — consumer or server, which are separate panels rather than two halves of one list. A standalone panel holds no figures of its own; it selects among catalogue entries and reports the topology note rather than a headline number, because two of these systems are tiered and one is a cabled pair. They are exclusive because they answer different questions: one starts from a machine you already have in mind, the other from none. The gate's machine and browse doors preset the page, but the switch sits above the shared precision and context strip and is always present, so the door still decides where you open, never what you may see. Precision and context stay outside the split, because they are one decision for the whole instrument.
